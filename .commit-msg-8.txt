feat: T3.2 — PostGIS catalogue that never counts rows

Real database this time: the local PostgreSQL 17.5 / PostGIS 3.5.2, plus a
committed F7 fixture that has the shapes the plan calls out -- a table with NO
primary key, a GEOGRAPHY column, and a table deliberately left un-analyzed.

What landed (packages/gis-postgis)
- catalog.ts: geometry_columns UNION geography_columns, joined to pg_class so the
  relation kind and reltuples arrive in ONE round trip; extents from
  ST_EstimatedExtent, which reads statistics rather than data
- connect.ts: one pool per profile, opened with default_transaction_read_only=on
  and the profile's statement_timeout applied to the SESSION, every error
  redacted; a statement cap maps to SQL_TIMEOUT
- the service exposes catalog(profile) / layerMetadata(profile, layer) / close()

Verified against the live server (check:postgis-live, 20 assertions), including
the acceptance criteria themselves:
- NO count(*) is ever sent -- asserted on the RECORDED TRAFFIC, not on the code
- an un-analyzed table reports UNKNOWN (-1) rather than zero, WITH an actionable
  reason ("run ANALYZE"), and is still listed
- the catalogue is one round trip, not one query per layer
- geography layers are found (they are absent from geometry_columns entirely)
- the session is read-only and the statement cap is in force

Two traps the real server caught immediately, now contracts #46/#47:
- geometry_columns uses the legacy f_-prefixed column names in PostGIS 3.x
  (table_schema does not exist), so the first query was rejected outright
- its type column is UPPERCASE while every other layer here speaks GeoJSON, and
  "capitalize the first letter" is wrong for exactly the compound names that
  matter (MULTILINESTRING -> Multilinestring). An explicit table fixes it.

PostGIS checks green.
