## 四、🔴 真库抓到的两个坑（单测永远抓不到）

1. **`geometry_columns` 用的是 `f_` 前缀的旧列名**（`f_table_schema`/`f_geometry_column`），现代拼写 `table_schema` **不存在** ⇒ 第一条查询直接被服务器拒绝（契约 #46）。
2. **目录里的几何类型是大写**（`POINT`/`MULTIPOLYGON`），而本仓其余各层说 GeoJSON 的 `Point`/`MultiPolygon` ⇒ 比较会**永远不匹配**。修法是在边界归一化；且**不能靠首字母大写**（`MULTILINESTRING` → `Multilinestring` ✗），必须是显式表（契约 #47）。

## 五、诚实边界

1. **目录尚未接入 inspect/query/render 链路**：T3.2 交付的是 host 侧可调用的目录；把它变成 `gis_inspect` 的一个剖面、以及分页查询（T3.3）、服务端 MVT（T3.4）、多图层贯通（T3.6）都还没做。
2. **不知道 PK 与列清单**：目录只报空间列；「无主键表怎么分页/导出」要等 T3.3 设计（fixture 已经把这张表准备好 ✓）。
3. **`SQL_TIMEOUT` 的映射未在真库验证**：错误码已在 `connect.ts` 里按消息判定，但本轮的检查只验了 `SHOW statement_timeout`，**没有真的跑一条超时语句**（T3.3 的判据，届时补）。
4. **bundle 行仍未挂**：给新包加行需要有重装 profile 这一步，仍未做（T3.1 记录的边界 4 继续有效）。
5. **fixture 落在用户本机 PG 的 `dsh_gis_fixture` schema**：检查每次 DROP+CREATE 该 schema ✓，不触碰其它对象 ✓。
6. **凭据用的仍是检查内联的假解析器**（`pg_live` → `postgres`）：`check:postgis` 已经验过真 `LocalCredentialProvider` 路径 ✓，本轮不重复。
