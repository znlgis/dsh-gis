## 三、两个设计决定

1. **门槛用于「诊断」，不是用于「执行前拦截」**：本构建**只读**（计划明说），所以**写门槛存在的意义是解释为什么没有编辑功能** ✓ ——GDAL 够新就报 `gdb.write.available` 并附上 `readOnly: true`；够旧就报 `gdb.write.too-old` 并给出「找到了什么 / 需要什么」✓。
2. **答案是「键 + 数字」，永远不是成句的文案** ✓：在这里拼句子无法翻译，而且测试一旦断言句子，每次改进措辞都会挂 ✗。调用方拿到 `{ key, detail }` 自己渲染 ✓。

## 四、实测（单测 12 + 真 GDAL 13）

- 版本解析：真字符串 `GDAL 3.13.3 "Iowa City", released 2026/08/13` ✓、开发版 `3.11.0dev-abc1234`（**如实标记 development** 而不是当成发布版 ✓）、两段式 `3.6` ✓、垃圾输入 → `undefined` ✓
- **边界断言在边界上**：1.11 通过 / 1.10.9 拒绝 ✓；3.6 通过 / 3.5.3 拒绝 ✓；更高主版本恒通过 ✓
- 诊断键：`gdb.read.too-old`（带 found/need）✓、`gdb.driver.missing` ✓、`gdb.read.ok` ✓、`gdb.write.available` + `readOnly: true` ✓、`gdb.write.too-old` ✓
- **版本不足时不执行外部程序** ✓（用记录型 runner 断言**零次调用** ✓）
- 真机：OpenFileGDB **存在** ✓、版本解析为 3.13.3 ✓、读门槛通过 ✓、committed fixture `cities.gdb` 枚举出 `cities_gbk`（Point）✓
- **不实现写** ✓：模块导出的**函数**里没有任何 write/create/update/delete/insert（`writeDiagnostic` 只描述能力 ✓）——结构化的承诺比文档里的承诺强 ✓

## 五、诚实边界

1. **fixture 只有一个要素类**：计划 F6 要的是**多要素类**的 `.gdb`；T3.6（多图层贯通）需要一个两三层的新 fixture，本轮没造（造它属于 T3.6 的判据）。
2. **图层枚举走 `ogrinfo -json -so`**：读的是**摘要**（不含字段清单与范围）✓；需要字段/范围时得再来一次查询（T3.6 视需要）。
3. **`OGR_ENABLE_PARTIAL_REPROJECTION` 等 GDAL 配置面未碰** ✓。
4. **未测「驱动存在但读失败」的真实路径**（例如损坏的 `.gdb`）——代码里有 `DATASET_UNREADABLE` 分支，但没有对应 fixture。
5. **`probeGdbSupport` 每次调用都问一遍 GDAL**：没有缓存（真机上是两次进程启动 ≈ 100 ms）✓；接进设置卡片时应缓存。
