# dsh-gis 实施计划

> 本计划把 [方案设计.md](./方案设计.md)（v2，16 章 + 8 附录）转成可执行工单。**设计回答「是什么、为什么」，本计划回答「谁、何时、怎么算做完」。**
>
> **估算口径**：1 人周 = 5 人日；面向「熟悉 TypeScript 但**不熟悉 DSH 内部**」的工程师，**含自测**，不含评审等待与外部依赖等待。
>
> ⚠️ 本计划是**自下而上**重估的：逐任务拆完后合计 **≈85.5 人日 ≈ 17.1 人周**，比设计文档路线图的 ≈14.5 人周高约 18%。差值与取舍见第十节——这是本计划相对设计文档的第一个实质修正。

### 完成过程中对计划的修正（**重要，后续排期请以此为准**）

| # | 计划原文 | 实测结论 | 影响 |
|---|---|---|---|

| 2 | T1a.6 依赖 `geotiff.js` / `turf` | 未引入。M1a 的范围不需要它们 | 依赖面比计划小 |
| 3 | T1a.12 出图 | 用 **Node 内置 `zlib` 手写 PNG + 手写光栅化**，零新依赖 | T1a.12 成本低于估算 |
| 4 | 新增（计划中没有） | **`gis_doctor` 工具**：让探测结果可被模型使用 | M1b 必要补充 |
| 5 | 新增（计划中没有） | **`docs/运行时契约.md`**：26 条契约陷阱（T1a.2 新增 18–20：存储域生命周期 / 可选依赖 / 跨包错误判定；T1a.10 新增 21：异步初始化的冷路径；T2.1 新增 22–23：第三方浏览器库的 worker 装载 / CJS 动态 import 不能变懒 chunk；T2.2 新增 24–25：跨图的共享模块 / 陈旧 chunk；T2.3 新增 26：浏览器字节路由的栅栏与 exact path） | 实现新组件前必读 |
| 6 | 「必须起真实实例才能验证」 | **不完全成立**。M1b 的 GDAL 链路靠把 `runtime.run` 抽成接口，在单元测试里驱动了**真实二进制**，不需要凭据 | 后续里程碑应优先寻找这种解耦点，可显著降低验证成本 |
| 7 | T1a.2 起步资料建议「不加进 inject、用 `ctx.get` 可选访问」 | **方向对、写法更优**：`ctx.inject(['storageDomain'], cb)` 才是可选依赖（服务出现即挂载、消失即卸载，且不用轮询）；另有一处偏离设计 §95——`dsh-storage-domain` 走 `dependencies` 而非 peer，理由见执行记录 | 后续「可选依赖」一律用 `ctx.inject`；`registerDataset` 由同步变 async，`inspect/query` 改为走 `resolveFresh`（解析即校验） |
| 8 | T1a.10 只写「配额 + LRU」 | **缓存的形状由下游决定**：T2.4 的 COG 是分钟级、带进度、可取消、先查配额，所以 API 做成 `begin(估算)→写 staging→commit/abort` 两段式，而不是 `put(bytes)` 一种 | 大产物永远不进内存；取消/崩溃留下的半成品不会被当成命中 |
| 9 | 「真实实例验证」的隐含前提 | **profile 加载的是 `lib/`（构建产物），不是 `src`**。第一次跑 T1a.10 的实例验证时源码已修、忘了 `pnpm build`，同一个失败又出现一次 | 每次真实实例验证前先 `pnpm build`；反过来说，这也保证验证的是用户真正拿到的东西 |
| 10 | 计划未指定 MapLibre 版本 | **必须锁 5.x**：6.x 是纯 ESM 且用 `new URL('./maplibre-gl-worker.mjs', import.meta.url)` 取 worker，而插件 chunk 由 `/plugins/<pkg>/...` 提供、那个兄弟文件不存在 ⇒ 地图静默初始化失败。5.x 的 UMD 把 worker 内联成 blob | 依赖写死 `^5.24.0`；`pnpm check:bundle` 把这个前提固化成断言 |
| 11 | 「`import()` 会变成 `require.async`」 | **前提是目标模块是 ESM**。对 CJS 包（maplibre 5 是 UMD）动态 import 会生成 `__toESM(require(...))`，预设的重写规则匹配不上，**直接构建失败**（幸而是响的） | 用一层 ESM 包装模块（`map/maplibre.ts`）承载互操作，调用点保持 ESM 动态 import |
| 12 | 契约 #10 只点名了共享 CSS Module | **任何模块都算**：eager 图运行时 import 一个 lazy 图的模块 ⇒ 共享 chunk ⇒ 入口同步 require ⇒ 工厂抛错 ⇒ **插件样式标签整批消失**（症状是「插件没加载」）。修法：lazy 图模块只允许被 eager 图**类型导入** | 已写进卡片源码注释；产物检查新增「入口不得静态 require chunk」与「无孤儿 chunk」两条 |
| 13 | 「构建成功 = 产物自洽」 | **不成立**：`clean: false`（有意）会让离开依赖图的旧 chunk 留在 `lib/` 并被 `files` 发布 | 构建前 `scripts/clean-client-chunks.mjs`；产物断言「每个 chunk 都能从入口到达」 |
| 14 | 路由写在哪个包 | 计划未指定（交付物清单里没有 http 包） | 放在 **`ui-gis` 的宿主半**：它就是「浏览器面」的家（DSH 的 `ui-deliverables` 同理），且已在 bundle 行里；`inject: ['connection','gis']` 让没有浏览器面的 profile 自然等待 |
| 15 | 「共享 chunk 只由跨图共享引起」（修正 #12） | **还有第二种触发器**：一个模块被**两个动态导入者 + 一个静态导入者**引用，同样会被提升成独立 chunk，于是**卡片 chunk 同步 require 组件 chunk**（T2.6 实测，`check:bundle` 报出） | 撤掉 T2.1 的开发按钮（它本就写着「直到卡片落地为止」）；判据固化为「无同步 chunk require + 无孤儿 chunk」 |
| 16 | `output.presentationMeta` 返回 JSON | **TS 的 `interface` 没有隐式索引签名**，所以「看起来完全 JSON」的接口并不满足契约的 `JsonValue`（编译器的原话：Index signature for type 'string' is missing） | JSON 面向的类型用 `type` 别名而非 `interface`；已在源码注释里写明 |
| 17 | 「卡片的浏览器级验证需要模型凭据」 | **不需要**：DSH 自带 `@deepseek-ai/dsh-llm-mock-server`（`pnpm run mock:llm`，行为含 `tool_call_success`），把 provider 指向它即可在**无 key** 的情况下驱动一次真实 `gis_render` 调用 | M0/T0.3 与 M1b 留下的「需要凭据」边界有了解法；**T2.10 的 Web e2e 走这条路**（手写 zstd 会话日志比它贵得多） |
| 18 | `@testing-library/react` 的 peer 自动安装 | **会装成 react-dom@19** 而本仓库是 react@18 ⇒ 导入期 `TypeError: Cannot read properties of undefined (reading 'S')`，报错看不出根因 | 把 `react-dom@^18` 显式钉进根 devDependencies |
| 19 | T2.10 判据写「纳入 `pnpm test:web`」 | **有意偏离**：`test:web` 是 1.6 秒的 DOM 车道（任何机器可跑），而真实浏览器 e2e 需要 Chromium + 隔离实例 + 约 3 分钟 | 做成独立的 `pnpm check:e2e`，与 `check:real`/`check:route`/`check:browser` 并列；**T5.3 的 CI 把它作为独立阶段** |
| 20 | 「字节路由缓存对谁都好」 | **immutable 的字节路由会让可用性探测被浏览器缓存回答**，把失效 id 报成「还在」（T2.10 实测） | 探测显式 `cache: 'no-store'`——它问的是源站；缓存里的旧字节对那个 id 本来就是对的 |
| 21 | 计划/设计里的 `gdal_translate -of COG -progress` | **GDAL 3.13.3 已删除 `-progress`**，传了直接 `ERROR 1: Unknown argument`（进度默认就打） | argv 不带该开关，进度解析默认输出；外部工具的**每个**参数都要在本机那版上真跑一次（契约 #27） |
| 22b | 「chunk 之间同步 require 是正常产物」 | **不是**：loader 的 `require` 只认平台种子、已物化的模块、已登记的 factory ⇒ 同步 require 另一个 chunk **只在它恰好先加载时**才成立（rolldown 一遇到「两个动态 chunk 共享模块」就这么发）。内核升到 rc.1 后**整条地图路径不再渲染**（T2.5 实测，产品自己报出 load 错误） | 构建后处理 `scripts/flatten-client-chunks.mjs`：把被同步 require 的 chunk **内联**进引用者并删文件（仍走 `require.async` 的保留）；判据固化为产物契约「无 chunk 同步 require chunk」 |
| 22c | 「`exports` 的 `browser` 条件会优先」 | **条件按包里的书写顺序匹配**：geotiff 把 `import` 写在 `browser` 前 ⇒ 客户端包进的是 **Node 版**，经 `web-worker` 摸到 `http` ⇒ `require("http") missed the module table` | 预设里显式指向该包自带的 browser 构建（`BROWSER_BUILD_PREFERENCE`）；UMD 的动态导入再套一层 ESM 包装模块 |
| 22d | 「peer 版本不匹配会报错」 | **不报错，是静默跳过**：内核从 0.1.7-alpha.2 漂到 rc.1 后，`dsh` 打印「skipping profile bundle」而**不加载整个插件**——所有实例检查同时红，看起来像插件自己坏了 | 内核升级的标准动作：升齐 pin → `pnpm install` → 全量测试 + 六条实例检查（本轮实测：仅需升版本，无 API 破坏） |
| 22e | 「依赖里用不到的 Node 代码路径无所谓」 | **会毒死整个 chunk**：pmtiles 的 `FileSource` 在模块顶层调 `require("module").createRequire` ⇒ 浏览器里 `require("module") missed the module table`，整块加载失败（T2.5 实测） | 客户端预设为 Node 内置提供**桩模块**（调用/读取即抛）；有 browser 构建的依赖仍优先指过去 |
| 22f | 「范围总是宿主知道」 | **自带索引的容器只有读了才知道范围**：FGB/PMTiles 在宿主侧没有 bbox | `bbox` 允许为空数组，含义是「客户端自框定」；空 extent 在规范化里不算缺陷，客户端按读到的数据 `fitBounds` |
| 22g | 设计 6.5 的 `session.append('gis/layer', …)` | **仓外插件做不到**：读路径拒绝未知事件类型，而 `Session.append` 不暴露 `ignorable` 标记 ⇒ 自造类型的日志换构建就读不出来（T2.9 实测） | 改为折叠**已有**的 `tool/result`（地图描述本就在其 `meta` 里）——不需要新词汇，且「唯一事实来源在日志」按构造成立 |
| 22h | 「压缩日志文件直接解压即可」 | **持久化 JSONL 是多帧 zstd**：一个帧只装头部，`zstdDecompressSync` 与 `createZstdDecompress` **都不跨帧** ⇒ 看起来像「日志里没有事件」（T2.11 曾误判为刷盘时机） | 按 magic 切帧逐帧解码，切不动就放宽；契约 #37 |
| 22i | 「调度器 chunk 一律不内联」（#31 的初版修法） | **太严**：共享地图组件既是调度器（按需加载读取器）又是两个预览体的依赖 ⇒ 放宽后 bundle 又出现被禁的同步 require（T2.8 实测） | 唯一跳过条件 = 「内联会自嫁」（目标能到达引用者）；共享组件因此内联进每个消费者，各下一份、互不牵连（契约 #39） |
| 22j | 「有概视图的大 COG 读起来很快」 | **实测不然**：8000×8000 的 COG（`gdal_translate -of COG` 默认建概视图）在 2048 px 窗口上限下仍要 **5259 ms**（普通 GeoTIFF 2723 ms、小 COG 33 ms）⇒ 主线程冻结 3–5 秒（Worker 化实测） | 栅格解码进 **Web Worker**：读取器以文本随 chunk 旅行、Blob URL 起 classic worker；只回原始样本，RGBA 展开留主线程（契约 #40/#41） |
| 22k | 「构建命令没输出就是成功」 | 新包缺 `tsdown.config.ts` ⇒ 产物在 `dist/` 而 `main` 指 `lib/`，退出码 0、无输出（T3.1 实测，白查三轮） | 断言**产物存在**（`Test-Path` / 真 `import()`），不是断言「没有报错」；契约 #43 |
| 22l | 「隔离里能注册 ⇒ Loader 里也能」 | 同产物在隔离 cordis 正常，作为 Loader 行却**服务不出现且无告警** | **真因：入口形状**——只有 `name`+`apply` 或**默认导出 Service** 才会被装配；只导出 `apply` 的模块静默不加载。改默认导出后实例检查 12/12 通过（契约 #42 结案） |
| 22o | 「LIMIT/OFFSET 就是分页」 | 无 `ORDER BY` 时顺序未定义：第 2 页可能重复/漏行且不报错；无主键表更是没有天然顺序 | 分页带排序键（主键→`ctid`，并如实报告），真库用「两页无重叠」验证；超限**拒绝**而不是静默截断（契约 #48） |
| 22n | 「PostGIS 目录用现代列名 / 类型可直接比较」 | `geometry_columns` 是 `f_` 前缀旧名（`table_schema` 不存在）；其 `type` 是全大写 `POINT`，而本仓其余各层说 GeoJSON 的 `Point` | 照真实列名写；类型在边界归一化且用**显式映射表**（首字母大写会把 `MULTILINESTRING` 变成 `Multilinestring` ✗）。两条都是**真库第一条查询**就抓到的（契约 #46/#47） |
| 22m | 「凭证引用随便起名 / 凭证文件格式随手写」 | `postgis-city`（连字符）+ 旧扁平 yaml ⇒ **凭证插件启动失败** ⇒ 整个 harness 起不来，报错却指向用户从没配过的插件 | 引用必须 `[A-Za-z_]\w*`、文档必须 `version: 1` + `refs:`；我们的 schema 已用同一正则前移拦截（契约 #44/#45） |

### T1a.2 的起步资料（**已完成**，2026-09-23）

> 结果与实测见 **[T1a.2-执行记录](./T1a.2-执行记录.md)**。下面是当初侦察到的 API（仍然有效，留作参考）；两条注意事项都已被采纳或被更优写法取代：
> 「`open()` 异步 + 域名单次占用」→ 实现里对 `already-open` **重试**（HMR 背靠背重载会撞上）；
> 「可选依赖不要进 inject」→ 用 `ctx.inject(['storageDomain'], cb)`，比 `ctx.get` 多了「服务出现/消失时自动挂载与卸载」。
>
> `ctx.storageDomain` 的 API：

```
declare module '@deepseek-ai/cordis' { interface Context { storageDomain: DomainFacility } }
  // 声明于 packages/storage/storage-domain/src/index.ts:35-39

class DomainFacility {
  async open<S extends DomainSpec>(spec: S): Promise<Domain<S>>
  // 生命周期：调用方持有返回的 handle，并负责 Domain.close()（通常作为自己的 ctx.effect 销毁器）
}

defineDomain<S extends DomainSpec>(spec: S): S            // spec.ts:107
interface Domain<S> {                                     // domain.ts:97
  table(name: string): KvTable<string, unknown>           // domain.ts:217
  close(): Promise<void>                                  // domain.ts:118
}
```

**两个必须注意的点**：

1. **`open()` 是异步的，且一个 domain 名只能开一次**（`already-open` 会抛错）。要在 `ctx.effect` 里打开并关闭。
2. **`gis-core` 目前用类形式，注入必须写成 `static inject`**（见运行时契约第 1 条）。若把 `storageDomain` 加进注入列表，**`gis-core` 就会等待该服务**——profile 若未挂载 storage，`gis-core` 将永远不激活。**建议做成可选依赖**：不加进 inject，改用 `ctx.get('storageDomain')` 之类的可选访问，缺省时退回内存注册表。

**已有的基础**（当时）：id 派生（`deriveDatasetId`，内容派生、稳定）与 `DATASET_NOT_FOUND` 结构化 404 语义都已实现并有测试；缺的只是把注册表落到 storage 并跨进程恢复。

**落地结果**：域 `gis` / 表 `datasets`（`per-record` + `backup-and-skip`），记录 schema 与 `Dataset` 双向映射在 `registry-domain.ts`，内存 + 可选持久在 `registry.ts`，装配与 `resolveFresh` 在 `index.ts`。**顺带修掉一个 id 派生缺陷**：shapefile 家族成员原先只把文件名编进身份，改 `.dbf`/`.prj`/`.cpg` 不换 id——现在成员的 size/mtime 也参与哈希。

## 十、与设计文档路线图的差异（自下而上重估结果）

| 里程碑 | 设计路线图 | 本计划 | 差异原因 |
|---|---|---|---|
| M0 + M1a | 1 + 2 = 3 人周 | 4.1 人周 | 格式层（WKT/SHP/GeoJSON）与 fixture 的真实成本高于按人周粗估 |
| M1b | 2 人周 | 2.6 人周 | 设置卡片是**客户端工程**，含后端检测通道 |
| M2 | 3 人周 | 3.2 人周 | COG 后台任务（进度/取消/配额）此前被低估 |
| M3 | 2 人周 | 2.2 人周 | 安全测试独立计 |
| M4 | 3 人周 | 3.4 人周 | 代理层与 SSRF 是两个独立工作包 |
| M5 | 1.5 人周 | 1.6 人周 | 基本一致 |
| **合计** | **≈14.5 人周** | **≈17.1 人周** | **+18%** |

**结论**：设计的路线图乐观约 18%。三个选项：

1. **接受 17 人周**（推荐）——数字来自逐任务拆解，比粗估可信；
2. **砍掉 M4**（−3.4 人周）→ 13.7 人周，且不影响任何其他需求；
3. **砍掉 T2.8 文档预览 + T3.4 服务端 MVT**（−4 人日）→ 再省约 1 人周。
