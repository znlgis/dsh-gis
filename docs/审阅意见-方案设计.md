## 1. 内部一致性（INTERNAL CONSISTENCY）

### 1.1 [P0] 设置页被指派到三个不同的插槽，而第十一章选的正是目录里明确说"不要用"的那个
- 为什么重要：§4 架构图写 `settings.section[gis]`；§3.3 表格把 `settings.section` 标为"设置页"；§11.4 却写"注册一张卡片到 `plugins.item`（Official 组里我们自己的条目）"。`slot-catalog.ts:2030-2034`（plugins.item）原文是 "One **official** plugin the Plugins page lists in its Official group … OCCUPIED by the official settings pages … **a bundle's configuration belongs in `plugins.bundle.config` or `plugins.row.config` instead**"。第三方插件挤进 Official 组既是错误的自称，也占用了为内置伴生包保留的座位；实现者按 §11.4 写会做错，按 §4 写会和 §11.4 冲突。
- 改法：确定唯一座位——bundle 级用 `plugins.bundle.config`（key = bundle 包名），行级用 `plugins.row.config`（key = `<包名>#<rowId>`）；删掉 §4 图和 §3.3 表里的 `settings.section` 说法，并在 §11 说明为什么不用 `plugins.item`。

### 1.2 [P0] §3.5 明文禁止了第八章强制要求的那条路由，且只有 §6.4 被标注"修正"
- 为什么重要：§3.5 写"宿主已经提供了四条把数据送到浏览器的路，**不要新造第五条**"，并把 `/api/file` 推荐给"GeoJSON / **GeoTIFF / PMTiles** 原样取用"。但 `/api/file` 是整文件读（`media-references.ts:45` `fs.readBytes(target, signal, maxBytes)`，超限 413、无 `Accept-Ranges`/`206`），PMTiles/COG 根本走不通；§8.1 于是要求自建 Range 路由，却只写了"对 6.4 的修正"，§3.5 的过期建议原样留着。实现者读到 §3.5 会照做，然后第二阶段推倒重来。
- 改法：把 §3.5 改成"宿主四种形态 + 插件自有 exact 路由一类"，删掉把它称为"第五条"的措辞，并在该处直接指向 §8 的路由表。

### 1.3 [P0] 同一条数据通道出现四种 URL 形状，其中三种在本平台上无法注册
- 为什么重要：§3.5 `/api/gis/datasets/<id>/geojson?bbox=&limit=`、`/tiles/<z>/<x>/<y>.mvt`；§6.3 `'/api/gis/datasets/' + datasetId + '/' + kind`；§8.1 `/api/gis/blob/<datasetId>`；§9.3 `/api/gis/service/<serviceId>/tile/<z>/<x>/<y>`。`ConnectionFetchRoute` 注释是 "One **exact**, transport-independent Fetch route"（`rpc.ts:143-153`），匹配是 Map 精确查 pathname（`rpc-host.ts:135,140`），同路径重复注册直接抛错（`rpc-host.ts:163-165`）。宿主自己的流式路由全部是字面常量 + 查询参数（`/api/present.open?sessionId=&seq=&index=`，`present-open.ts:104-111`、`presented.ts:7`）。**瓦片路由按路径段参数写，永远不会命中**；每个数据集注册一条 exact 路径则会在 id 变动/重扫时撞重复注册。
- 改法：给出一张唯一的路由表，全部用 exact path + query：`/api/gis/blob?id=&kind=`、`/api/gis/geojson?id=&bbox=&limit=`、`/api/gis/tile?service=&z=&x=&y=`、`/api/gis/features?service=&type=&bbox=&count=&startIndex=`；§6.3 的 `presentationMeta` 示例同步改成同一形状。

### 1.4 [P0] 清单、包名与配置字段三方不一致
- 为什么重要：§5 的 `cordis.patch.yml` 插入 `@znlgis/dsh-gis-core / -gdal / -tools / dsh-prompt-gis / dsh-ui-gis`，而 §5 的 `packages/` 列表里没有 `dsh-gis-tools`（只有 6 个 `tool-gis-*` 包），也没有承载 bundle 清单（`dsh.bundle.patch`）的根包 `@znlgis/dsh-gis`。配置字段更直接打架：§5 patch 写 `binDir`，§11.4 的 `Config` 写 `gdalBinDir`，§11.3 的发现顺序表也写 `gdalBinDir`。照 §5 抄，设置页绑定的字段名是错的。
- 改法：由一份"配置参考"（见 2.2）生成 patch 示例与 `Config`；patch 行与包一一对应；显式列出 bundle 根包。

### 1.5 [P1] 外部进程执行缝自相矛盾，而且 §12.3 的安全断言是错的
- 为什么重要：§10-L1 说 GDAL"通过 `ctx.shell` 调用"；§11.3/§11.4/§12.3 用 `ctx.subprocess.spawn({ argv, env })`；§14 风险 6 的缓解写"一律 `ctx.shell`；结构化 argv"。事实：`ctx.shell` 只吃**命令字符串**（`ShellExecSpec.command: string`，POSIX 上是 `bash -c`，见 `packages/shell/shell/README.md:56`），而 `ctx.subprocess` 才是"argv 从不经 shell 解析"的那条缝（`subprocess/src/types.ts:77-107`）。§12.3 说"两者都继承部署方的沙箱模式与审批策略"——**对 `ctx.subprocess` 不成立**：`packages/subprocess` 里没有任何 `sandboxPolicy` 引用，沙箱策略只在 `ctx.shell` 的 spec 上（`shell/src/types.ts:102,135-136`），且由具体执行器决定（"ignored by executors that do not confine"）。想同时拿到 argv 安全 + 沙箱，本平台的答案是第三条路：`ctx.sandbox.confine(argv, policy)` → 用它返回的 argv 去 `ctx.subprocess.spawn`（`packages/sandbox/sandbox/src/index.ts:153-176`）。文档从未提到 `confine`。
- 改法：把"如何起外部进程"收敛成一条规范路径（`confine` + `spawn({argv})`），删除"一律 ctx.shell"的说法，并把 §12.3 的断言改成实际情况（含"部署方未挂沙箱执行器时无隔离"这一事实）。

### 1.6 [P1] 第八章的子节号是 7.x、第十一章是 9.x，交叉引用已经产生歧义
- 为什么重要："9.3"同时指 §9.3「一律走宿主代理」和 §11.3「可执行文件发现顺序」；"7.1"同时指 §7.1「数据集 ≠ 文件」和 §8.1「五种零服务取数手段」。§7.4 的"走第八章的平铺/简化路径"、§13 的"见第十一节的纠正"都靠人猜。这是多次改稿留下的硬伤。
- 改法：重排子节号，并在被引用的位置加锚点；全文交叉引用改成"文件#锚点"。

### 1.7 [P1] 打包纪律条目计数错误，且指向一个不存在的章节内容
- 为什么重要：§3.1 标题写"三条打包纪律"，下面列了 4 条；第 3 条写"git 安装路径必须有自包含的 `prepare` 脚本（见第十六节）"，而 §16 全文 8 行只有三条命令，没提 `prepare`、`allowBuilds`、产物发布——相关内容只出现在风险 10。实现者按指引去 §16 会一无所获。
- 改法：改为"四条"，并把 `prepare`/`allowBuilds`/预构建产物策略写进 §16（见 2.13）。

### 1.8 [P1] 规范性内容成段重复，注定漂移
- 为什么重要：§9.4 ≡ §12.8（web.fetch 不可用）、§9.5 ≡ §12.12（SSRF）、§7.6 ≡ §12.11（PostGIS 注入/超时）、§8.3 ≡ 风险 13（缓存配额）、§12.5 ≡ 风险 4（返回量上限）。§9.4 与 §12.8 几乎逐字相同——文档已经证明了自己会重复抄。约 15% 篇幅是这份重复，且两份一旦分叉读者无法判断哪份有效。
- 改法：规范只写一处（安全规则集中在 §12），其余位置改成一句结论 + 链接。

### 1.9 [P1] 第 0 步的"退回"分支直接删掉一条硬需求
- 为什么重要：§1 写"设置卡片是客户端工件、**不能省**"，§13 第 0 步第 6 条却写"若第 3 点走不通，退回…**放弃**交互地图与**设置卡片**，改为文档化的手工配置"。也就是说：最大风险的兜底方案正好违反了需求清单里的"提供设置页"。这不是降级，是需求不满足，需要显式签字而不是藏在 spike 的判定里。
- 改法：写明"两项客户端的失败后果不同"：地图卡片失败→可降级；设置卡片失败→需求 7 不满足，必须升级为阻塞项或走 §16 的 profile patch 手工配置并同时修改需求。

### 1.10 [P2] 工具清单在各章名字对不上
- 为什么重要：§4/§6.2 用 `gis_crs_*` 分组，实际却是 `gis_crs_describe` + `gis_transform_point`（前缀不同）；`gis_connections`（§7.8）、`gis_env`（§11.2）、5 个 `gis_service_*`（§9.10）都没进 §4 图和 §6.2 表；§4 画了 `gis-mcp` 包，§5 的树里没有，§10-L4 又说 MCP"无需本项目写代码"。
- 改法：一张总表统一命名（建议全部 `gis_` 前缀 + 动词），删掉 `gis-mcp` 方框，MCP 只保留"预设文档"这一项交付物。

### 1.11 [P2] §1 的"三条主线"表格实际有五行
- 为什么重要：这是文档反复叠加编辑的直接证据，也说明"结论先行"一节已不再可信。
- 改法：重写该段，或直接删表。

## 2. 缺口（GAPS）

### 2.1 [P0] 没有汇总的工具清单
- 为什么重要：工具散在 §4、§6.2、§7.8、§9.10、§11.2、§13 六处；没有逐工具的 `parameters`（DSH 的 `ParameterSchemaSpec` DSL）、默认值、是否后台化、`presentationMeta` 键、错误码、可见性。可辨识联合的 `ToolArgsMap` 是 PTC 的输入契约，写不出来就无法实现注册表，也无法写 §15 的契约测试。
- 改法：新增一张工具总表（名称/参数+默认/输出 schema 形状/错误码/前后台/所属阶段），作为唯一事实源。

### 2.2 [P0] 没有配置参考
- 为什么重要：§11.4 只列了 9 个 `Volatile` 字段，但 §9.5 的"设置里显式放行内网"、§9.8 的 TTL/手动刷新、§12.4 的响应体上限与重定向上限、§7.3 的默认 `encoding`、§12.5 的 `maxFeatures`/简化容差、底图与代理设置——全都被描述成"可配"，却没有对应字段。同时 `Volatile` 与 §5 patch 里的静态 `config` 是什么关系（谁是默认值、谁被用户覆盖）没有解释。
- 改法：一份配置表（字段/类型/默认/作用域/是否 secret/所在 profile 行），并说明"patch 给默认、`.volatile()` 给用户层"的关系；正文里每个"可配"都要回指该表。

### 2.3 [P0] 没有规范值的 TypeScript 类型
- 为什么重要：`bbox`、`crs`、`dataset`、`layers[]`、`issues[]`、`truncated` 在多章里各有形状；§7.1 明确要求"可辨识联合"，却从没给出判别字段名（`kind`? `form`?）。服务定义包 `gis-core` 的全部价值就是这个类型集，它现在是散文。
- 改法：把 `packages/gis-core/src/types.ts` 的真实声明写进文档（Dataset 四态联合、Crs 来源联合、Bbox、GisIssue、GisResult 包装）。

### 2.4 [P0] 没有错误码体系
- 为什么重要：全文只出现过 `GDAL_UNAVAILABLE`、`TOOL_TIMEOUT`、`SANDBOX_UNAVAILABLE` 三个，且是顺带提及；而 §9.11 要"给明确状态"、§12.5 要"如实回 truncated"、§15 要断言错误语义、§7.8 的 `issues[].code` 需要取值域。没有码表，"如实报告"就退化成自由文本。
- 改法：一张 `GIS_*` 码表（码 / 触发条件 / 是否可重试 / 面向模型的一句话 / 面向用户的修复建议），并规定 `issues[].code` 与工具失败态共用同一套码。

### 2.5 [P0] 数据集 id 的生命周期与回放语义完全没写
- 为什么重要：§6.3 把 `presentationMeta` 里只放路由当作"回放可复现"的依据，§13 第二阶段的验收是"会话回放后卡片仍可重现"。但注册表被描述为宿主进程内的（§6.4 末段），只有 OGC 服务定义明确落 `ctx.storageDomain`（§9.11）。重启后、换个会话、源文件被移动或改名之后，卡片里的 id 会解析成什么？文档没有答案，而这是"展示"这条主线的地基。
- 改法：明确注册表持久化位置、id 的派生规则（路径+mtime+size？不透明随机？）、重扫后 id 是否稳定、解析失败时卡片显示什么（404 语义 + 兜底文案）。

### 2.6 [P0] 聊天卡片与工作台之间如何共享地图状态没有定义
- 为什么重要：§6.4 L2/L3 只提到 `ctx.sidebarRight.openResource(address, { params })` 和 `ctx.layout.selectPanel(id)` 两个动作，没有定义 address/params 的结构、没有定义共享 store、也没有说清"卡片里的这张图"怎么变成"工作台里的那张图"（同图层？同视图？同选中要素？）。§3.2 已经列出 `ctx.sessionProjections.register` 这条正路，正文却没用它。
- 改法：补一节"地图状态模型与流转"：状态类型（view/layers/selection）、存放位置（session projection vs 客户端 store）、卡片→工作台→右栏的传递协议。

### 2.7 [P0] 模型无法在运行时发现"这个部署能做什么"
- 为什么重要：§6.1 的系统提示词是静态文本，§7.8 只在 `gis_inspect` 的返回值里带 `capabilities`。模型在第一轮无从知道本机有没有 GDAL、OpenFileGDB 驱动在不在、QGIS 装没装、PostGIS 连不连得上、哪些 `gis_service_*` 工具可用——只能靠试错。§2 也承认"没装 GDAL 要变成可降级的运行时事实"，但没有任何工具把这个事实暴露出来。
- 改法：第一阶段就提供 `gis_capabilities`（或把 `gis_env` 扩成能力清单）：已注册 Provider、探测到的版本、可用驱动/格式矩阵、连接状态、当前降级档位；并在 `prompt-gis` 里要求模型先查它。

### 2.8 [P0] 远端服务在 CI 里怎么测：完全空白
- 为什么重要：§15 的单测/集成/E2E 三段里没有一个字涉及 WMS/WMTS/WFS；而这两条恰恰是最容易静默出错的（轴序、矩阵映射、Y 翻转、GML 剖面、分页）。仓库里给别的缝准备了 `llm-replay`/`remote-mock`，OGC 侧却什么都没规划，也没有"CI 禁止真实出网"的规则。
- 改法：录音式 fixture（若干真实 GetCapabilities/GetTile/GetFeature 响应，脱敏后入库）+ 一个本地 fixture HTTP 服务；契约测试覆盖 1.1.1/1.3.0 轴序、ScaleDenominator 映射、非 256 瓦片、越界不请求、GML 不支持构造报错；CI 用离线模式。

### 2.9 [P1] 国际化（i18n）没有章节
- 为什么重要：文档里已经出现 `locale: NS`、`t('title')`、`inject: ['locale']`，但没有任何关于资源注册、支持语种（zh-CN/en？）、文案归属、以及**服务端产生的诊断文案**（安装指引、错误建议）如何本地化的约定。DSH 的 README 是有中英双语的硬约定的（`README.i18n.yaml` 配对校验），插件若只出中文会与宿主体验割裂。
- 改法：补一节 i18n：客户端资源注册方式、服务端消息的本地化策略（返回码 + 文案键，而不是拼好的中文句子）、首批语种与验收。

### 2.10 [P1] 没有性能预算，验收里的"秒开"不可测
- 为什么重要：第二阶段验收写"首屏秒开"，第一阶段写"正确"，WMS 写"位置正确"——都不是可测阈值。没有 bundle 体积、数据集扫描、瓦片首字节、`maxFeatures` 默认值、简化容差、内存上限的任何数字，性能就只能在事后争吵。
- 改法：每条主线给出数字预算（如：客户端 chunk ≤ X KB gzip、首屏瓦片 P95 ≤ Y ms、`gis_query` 默认 limit=Z、几何简化容差默认值），并把这些数字写进阶段退出条件。

### 2.11 [P1] 版本化与状态/设置 schema 迁移没有交代
- 为什么重要：风险 2 只说"声明 `engines.dsh` 范围"，没给具体值；`ctx.settings` 的持久化字段、`ctx.storageDomain` 里的数据集/服务定义、缓存目录布局，都会随版本变化而出现"旧数据 + 新代码"。DSH 内核是 alpha（§1 自述），升级必然发生。
- 改法：定义插件 semver 与 `engines.dsh` 具体范围、持久化结构里的 `schemaVersion`、迁移函数的位置与失败策略（拒绝启动 vs 丢弃重建），以及"缓存不可迁移，直接失效"的明文规则。

### 2.12 [P1] 没有"明确不做"清单
- 为什么重要：禁止项散落各处（不做 WFS-T、GDB 只读、不发布服务），既不成体系，也没有被 §15 的验收覆盖，实施中最容易被"顺手加一个"。缺失的典型项：不编辑要素、不做制图排版/打印、不做栅格分析/分类、不发布任何瓦片服务、不做 3D、不代管远端凭证的申请与续期、不做 E-GDB 直连。
- 改法：加一节 "v1 明确不做"，并在验收表加一行"上述能力不出现在工具清单里"。

### 2.13 [P1] 插件自身的许可与分发没有内容，而 §16 只有 8 行
- 为什么重要：仓库 LICENSE 是 MIT（§2 已确认），但文档没说发布产物是什么许可；第三方代码会被**内联进 `lib/client.js`**（MapLibre/deck.gl/pmtiles/geotiff.js…），这类分发需要随附版权与许可声明（NOTICE/attribution），网页端还可能有署名要求；`files`/`exports` 内容、CI 发布流程、版本号策略、"git 安装需要 `allowBuilds`"的用户告知（风险 10）都只在风险表里提过一句。§3.1 让读者去 §16 找 `prepare`，那里什么都没有。
- 改法：扩写 §16：产物清单与 `files`、许可与第三方声明（含生成方式）、版本与 `engines.dsh`、npm/tarball/git 三条安装路径的差异与用户操作、CI 发布与 Windows 验证。

## 3. 不可行/代价被低估（INFEASIBILITY）

### 3.1 [P0] 第 0 步验证的是错的风险
- 为什么重要：§3.7 的"捷径"是手写一个 `client.js` 验证格式（fixture 只有 46/109 行）。但手写文件验证不了真正的工程量：React external 与冻结模块表对齐、`require.async` 懒加载 chunk（MapLibre/deck.gl/geotiff worker）、CSS Modules 样式注入（`tsdown.client.ts:1-11` 明说 CSS 由 lightningcss 在 bundle 内编译并注入）、source map、combo URL 与 rev。手写能过，只证明"格式是手写的"，不证明"能构建出一个真 UI"。
- 改法：spike 的出口条件改为"用真实打包器（复制 `packages/client/tsdown.client.ts`，替换它引用的 3 个仓库内模块）产出**两个组件、两个 chunk、带样式**的 bundle，在 GUI 里验证懒加载与 HMR"；手写样例只作为格式对照，不作为出口证据。

### 3.2 [P0] "最大风险"的定性有一半是错的：格式有文档，缺的是未发布的 preset 文件
- 为什么重要：§3.7/§14 风险 1 把客户端半描述成"必须自己复刻构建产物格式"，§3.7 末尾更声称"DSH 的 `docs/user/develop/` 没有任何一篇讲客户端 UI 插件"，据此"按读源码估工期"。事实：`docs/cookbook/adding-a-settings-card.md`（中英双语）完整讲了设置卡片的做法，包括宿主提供的 `form.state` / `form.mutate(operations, expectedRevision)`；`packages/client/modules/README.md`（144 行，双语）写清了 lazy-CJS 工厂、boot graph、`require.async` 兄弟 chunk、combo URL 与 HMR；另有 `docs/subsystems/client-modules.md` 与 `packages/client/AGENTS.md`。真正未发布的是 preset **文件**（它 import 了 `./modules/src/client/manifest.ts`、`./web/src/platform.ts`、`../../scripts/*` 三个仓库内模块）。
- 改法：把风险重新表述为"复制 preset 并替换三处仓库内 import（+ 与上游 API 漂移）"，据此重估客户端工期；同时把 §3.7 的"文档缺口"改成"文档分散在 cookbook/subsystems/AGENTS 三处，需要拼"。

### 3.3 [P0] 一个插件要占 10 个客户端面，不是小团队首版能承担的
- 为什么重要：§4 与 §3.3 计划了 `tool.call.toolview`、`main`+`sidebar.panellist`、`sidebar.right.pane.tab`、`sidebar.right.tab.document`(+2 卫星)、`conversation.view`、设置卡，外加可选的 `shell.overlay`、`deliverables.file.actions`、输入框 dock。每个面都要布局、空态/错误态/加载态、`--dsw-alias-*` 主题适配、键盘可达性，以及 §3.6/§15 要求的 HMR 安全测试；而它们之间还没有共享的地图组件与状态层。这是 5 个独立 UI 产品的工作量。
- 改法：首版只保留两个面——`tool.call.toolview[gis_render]`（聊天卡片）与 `sidebar.right.tab.document[gis-map]`（文件预览），并把共享的地图组件/状态层作为前置；其余面移出 v1。

### 3.4 [P1] 代理层的真实工作量没有立项
- 为什么重要：§9.3 用三句话决定了"一律走宿主代理"，但代理一旦存在，宿主就必须是一个正确的 HTTP 客户端：连接/读取超时、重定向上限、响应体上限、并发与限速、重试退避、按服务的凭证注入（apikey/Basic）、缓存键要含凭证作用域、`Attribution`/`Fees` 的展示义务。路线图里没有任何一项对应这些工作。
- 改法：把"OGC 代理基础设施"列成独立工作包，配自己的退出条件（黑洞超时、重定向环、超大响应、并发压测各一条测试）。

### 3.5 [P1] SSRF 防护只写了"默认拒绝私网"，挡不住常见绕过
- 为什么重要：§9.5/§12.12 的规则是注册时校验 URL 主机。实际风险在第二次解析：DNS rebinding（注册时解析到公网，取瓦片时解析到 127.0.0.1）、IPv6（`::1`、`fc00::/`、`fe80::/`）、十进制/八进制 IPv4 写法、`0.0.0.0`、以及 302 跳到私网。§9.4 已经确认不能依赖宿主 seam，这些就得自己写。
- 改法：改成"每次请求前解析 → 只允许全球单播地址（显式排除全部私有/环回/链路本地/IPv6 对应段）→ 用解析结果直连 → 重定向同协议且逐跳复检 → 上限次数"，并把 DNS rebinding 写进风险表。

### 3.6 [P1] 全文没有工作量模型
- 为什么重要：唯一的估算只有第 0 步的"2–3 天"。第五阶段（GetCapabilities 流式解析 + 归一 + TTL 缓存、WMS→瓦片适配、WMTS 矩阵映射含 Y 翻转与非 256、轴序归一、SSRF、代理、5 个工具、工作台混排）在业界是独立子系统级别的投入；第四阶段（PostGIS + GDB + 服务端 MVT）同样。没有工时与人力，路线图的"每步都能独立交付价值"无法验证，也无法决定砍什么。
- 改法：每阶段给出人周区间、假设的人力（几个人、什么角色）与最大的未知项；若人力是 1–2 人，按第四节的削减方案重排。

### 3.7 [P2] "2 GB GeoTIFF 秒开"忽略了转换成本
- 为什么重要：验收要求"只做一次 COG 转换"就秒开，但 `gdal_translate -of COG` 对 2 GB 栅格是分钟级、且缓存配额默认 5 GB（= 输入 2.5 倍），转换期间用户看到什么、失败怎么办、磁盘不足怎么办都没有交代。
- 改法：把"首次转换"建成一次显式后台任务（进度 + 取消 + 配额检查 + 失败诊断），验收区分"首次打开"与"再次打开"。

## 4. 过度设计（OVER-ENGINEERING）

### 4.1 [P0] v1 引入四套渲染栈：删掉 deck.gl、CesiumJS、OpenLayers、@loaders.gl
- 为什么重要：§10-L0 依赖表把 MapLibre、deck.gl、PMTiles、FlatGeobuf、CesiumJS、OpenLayers、@math.gl/web-mercator 全列为选型，第六阶段还要"deck.gl 大数据与 3D 场景"。四套渲染栈意味着四套坐标系/相机/图层模型、四份体积与四份 bug，而需求只要"展示与浏览"。
- 改法：v1 只留 MapLibre + geotiff.js + pmtiles（+ 纯 JS 解析）；删除 CesiumJS、OpenLayers、deck.gl、@loaders.gl 与 3D 相关段落。

### 4.2 [P0] 删掉 `conversation.view[gis]`、`shell.overlay` 与输入框 dock 入口
- 为什么重要：§15 的验收表没有一行对应这三个面——它们既不服务需求，也没有验收，属于"能加就加"。
- 改法：从 §4 图、§6.4 与第三阶段移除，放进"v1 不做"。

### 4.3 [P1] 删掉按需 MVT 金字塔（`ogr2ogr -f MVT`）
- 为什么重要：§8.1 的第五种手段与 §8.3 的缓存、§8.4 的降级、第六阶段的"按需 MVT 金字塔与缓存预热"互相牵连，但它要解决的事（大矢量分层显示）已经被 FlatGeobuf（bbox 流式）与 PMTiles（预生成单文件）覆盖，还额外要求一条 z/x/y 路由与一套瓦片淘汰。
- 改法：从 v1 删除；若客户端矢量渲染确有性能问题，再作为独立提案。

### 4.4 [P1] 推迟 DuckDB spatial 与 `qgis_process` 算法面板
- 为什么重要：§10-L2/L3 与第六阶段引入第二个 SQL 引擎（还要原生依赖 `@duckdb/node-api`）和 QGIS 算法面板；前者与 `gis_query` 功能重叠，后者是给极少数场景做的整套 UI。第一阶段能做到"探测到 QGIS 并调用 `qgis_process --version`"就已满足"以开源工具为主"的需求。
- 改法：两者移入"v1 不做/后续提案"。

### 4.5 [P1] 把 15 个包收敛到 7 个
- 为什么重要：§5 的 `packages/` 列了 15 个包（6 个 `tool-gis-*` + 8 个能力/provider 包 + `ui-gis`）。每个包都要 package.json/tsconfig/tsdown/测试/发布/版本对齐，而 DSH 的插件行是按包插入的，包越多 patch 与依赖矩阵越大。前五个工具共享同一套格式与 Provider 依赖，没有独立发布的理由。
- 改法：v1 收敛为 `gis-core`、`gis-formats`、`gis-gdal`、`gis-purejs`、`tool-gis`（一个包内注册全部工具）、`prompt-gis`、`ui-gis`；需要时再拆。

### 4.6 [P2] 五个内置技能砍到两个
- 为什么重要：§6.1 一次建了 5 个技能包（其中 `gis-web-map-publishing`、`gis-spatial-analysis-recipes` 描述的是本项目 v1 还不支持的能力）。技能是提示词预算，也是维护面。
- 改法：只留 `gis-format-conversion` 与 `gis-crs-troubleshooting`。

### 4.7 [P2] 删掉文档预览的卫星插槽
- 为什么重要：`.unpreviewable` 兜底入口与 `.actions` 导出按钮（§6.4-L1 末）依赖一个还没做的预览器，属于第二批的打磨项。
- 改法：推迟到预览器稳定之后。

### 4.8 [P2] 删除缓存预热与设置页的"锦上添花"项
- 为什么重要：`launchPrefix` 的图形化编辑、"查看将执行的确切命令行"、缓存预热、导出/导入设置，都是需求（配路径与环境变量）之外的装饰。
- 改法：v1 只保留路径、`extraEnv`/`unsetEnv`、"检测"按钮、配额与清空；其余推迟。

## 5. 路线图自洽性（ROADMAP COHERENCE）

### 5.1 [P0] 第一阶段依赖第 0 步那个会取消自己的分支
- 为什么重要：设置卡片被放在第一阶段，而它的技术前提是第 0 步的客户端构建；第 0 步第 6 条又说构建失败就"放弃设置卡片"。于是第一阶段的交付物取决于一个尚未判定、且判定为"否"时会被删除的前提——这不是排期，是悬空。
- 改法：把"客户端构建可行性"作为第 0 步的唯一出口门（通过/不通过），并在通过前不承诺第一阶段的任何客户端内容；不通过则先改需求（见 1.9），不要把它藏在 spike 里。

### 5.2 [P0] 第二、三阶段顺序颠倒，导致同一份地图组件写两遍
- 为什么重要：第二阶段做聊天卡片的 MapLibre 渲染，第三阶段才做文件预览与工作台。三者共用同一个地图组件、同一套图层归一化、同一套样式与加载态；先做卡片必然在第三阶段推倒重来（文档自己说第三阶段"含 `.unpreviewable`/`.actions`"与属性表分页，等于重画一遍）。
- 改法：合并为"浏览"一个阶段，先落地共享地图组件与图层模型，再依次接三个宿主面；或第二阶段只做服务端 PNG（已在第一阶段），把客户端全部推到合并后的阶段。

### 5.3 [P1] 第一阶段声称覆盖四种数据集形态，但 GDB 在第四阶段
- 为什么重要：§13 第一阶段要求"格式层覆盖 7.1 的四种数据集形态"，而 GDB（目录容器，多图层）在第四阶段才做。于是"多图层数据集贯通"这条最难的抽象在第一阶段只能靠 PostGIS（也在第四阶段）验证——四个形态里两个不在场，验收无法执行。
- 改法：要么把 GDB 只读（`ogrinfo` 探测 + 图层枚举）提到第一阶段，要么把"四种形态"从第一阶段验收里删掉，明确写成"单文件 + 文件族"。

### 5.4 [P1] 阶段退出条件不可测
- 为什么重要：第一阶段的"模型给出正确的 CRS/要素数/范围并交付一张图"、第二阶段的"首屏秒开"、第五阶段的"位置正确"都没有测试载体、fixture 与阈值；§15 的验收表是**需求**视角，不能替代**阶段**退出条件。
- 改法：每个阶段列出：可执行的验证命令/测试文件、使用的固定数据（fixture 路径）、可判定的数字或状态、以及"不通过时的处理"。

### 5.5 [P1] MVP 不够小
- 为什么重要：第一阶段包含 5 个工具、4 类格式、2 个外部工具 Provider（含发现链与真实探测）、缓存+LRU、系统提示词、3 个技能、服务端出图，以及一张设置卡片。按 3.6 的估算缺失，这已经是数月量级，却被称为 MVP。
- 改法：拆成 1a（无客户端）：`gis_inspect`/`gis_query` + WKT/GeoJSON/SHP + 纯 JS Provider + 服务端 PNG 走 `present` + 提示词分节；1b：GDAL/QGIS 探测 + 设置卡片 + `gis_env`/`gis_capabilities`。1a 不依赖任何客户端构建，风险与第 0 步解耦。

### 5.6 [P1] 缺少"发布/加固"阶段
- 为什么重要：没有阶段负责打包产物、CI（含 Windows，§14 风险 9）、许可证与第三方声明（2.13）、i18n（2.9）、干净 profile 上的安装验证、升级与迁移（2.11）。风险 10 提到的 `allowBuilds` 用户告知永远落不到工作项上。
- 改法：新增最后一个阶段"发布就绪"，退出条件：`npm pack` 内容清单核对、干净机器 + 空 profile 装一次、Windows CI 绿、第三方声明生成、`engines.dsh` 与迁移脚本存在。

### 5.7 [P2] 第六阶段"生态"是杂物桶
- 为什么重要：DuckDB、MCP 文档、deck.gl、MVT 金字塔被塞在一起，彼此没有依赖关系，也没有退出条件，实际是把"不想现在决定"的东西堆到了最后。
- 改法：删除该阶段；存活项（MCP 预设文档）并入"v1 不做/后续提案"清单并各写一句立项条件。

## 6. 结构（STRUCTURE）

### 6.1 [P0] 16 章 1085 行，形态与用途不匹配：参考材料与决策材料混在一起
- 为什么重要：实现者真正要反复查的是"扩展点事实、格式约束、路由契约、配置表、工具表、错误码"（§3/§7/§8/§9/§10/§11/§12/§15 的大部），而评审者要看的是"做什么、不做什么、怎么分期"（§1/§4/§5/§13/§14/§16）。现在两者互相夹杂，任何一处改动都要在千行里找；同时最该有的东西（类型、清单、码表、预算）反而没有。
- 改法：拆成 ①`docs/design.md`（≤400 行：定位、架构、范围与非目标、阶段与退出条件、风险）；②`docs/reference/*.md`（extension-points、formats、routes、tools、config、errors）；③`docs/acceptance.md`；④ADR 若干（客户端构建、OGC 客户端、设置与执行缝、缓存）。

### 6.2 [P1] 合并/删除：§3 降为附录，§12 去重，§14 瘦身
- 为什么重要：§3 大段复述 DSH 自己的文档与源码（插槽表、样例代码），会随上游漂移，且不是本项目的设计；§12 与 §7.6/§8.3/§9.4/§9.5 重复（1.8）；§14 的 25 条风险里，多数是 §12/§15 的改写（4、13、17、18、19、20…）。
- 改法：§3 收敛成"已核实的扩展点清单 + 文件行号"一页，放在附录；§12 作为唯一规范处；§14 只留 6–8 条真正的项目风险（客户端构建、上游 alpha、无 GDAL、远端服务不可用、SQL/SSRF、工作量与人力），每条要有触发条件、观察指标与负责人。

### 6.3 [P1] 拆分：§7 按格式拆，§9 独立成篇
- 为什么重要：§7 是稳定参考（每种格式的陷阱 + 降级矩阵），适合按格式拆成可独立引用的文档；§9 是"网络客户端"这一独立产品面，风险（SSRF、CORS、轴序、限流、署名）与其余部分正交，完全可以整体裁掉而不影响其它需求——把它单独成篇才能让评审者真正选择要不要做。
- 改法：`reference/formats/{wkt,shp,geojson,gdb,postgis}.md`；`design-ogc-client.md` 独立评审。

### 6.4 [P1] 移动：路线图提前，配置参考独立，验收移出
- 为什么重要：路线图在第十三章，读者要读到最后才知道范围；配置内容散在 §5/§11；验收表埋在 §15 里难以当作清单使用。
- 改法：§13 紧跟 §1；配置字段进 `reference/config.md`；§15 的验收表进 `docs/acceptance.md` 作为可勾选清单。

### 6.5 [P2] 删掉：§2、§1 的错标表格、"已核实"标记
- 为什么重要：§2 的两段事实可以并进 §1 的一句话；"本轮新增的三条主线"是历史痕迹（且标错行数）；"已核实"是作者的自我保证，不是读者可用的事实，且随时间失效。
- 改法：删除 §2 与错标表格；把"已核实"改成行内 `路径:行号` 引用。

## 结论：最重要的三处修改（按顺序）

**第一，先把"浏览器侧数据通道"这一层契约钉死，因为它现在写成了本平台无法实现的样子。** 用一张表定死 exact path + query 参数的路由（`/api/gis/blob?id=&kind=`、`/api/gis/tile?service=&z=&x=&y=` 等），删除 §3.5"不要新造第五条"与 §6.3/§8/§9.3 之间互相打架的四种 URL 形状，并补上数据集 id 的持久化、派生与回放语义——否则"展示/浏览"两条主线的地基、聊天卡片的回放验收、以及 COG/PMTiles 的 Range 路径全都是悬空的。

**第二，把 v1 砍到能交付的大小，并按真实人力重排阶段。** 删掉 deck.gl/CesiumJS/OpenLayers/@loaders.gl、`conversation.view`、`shell.overlay`、按需 MVT 金字塔、DuckDB 与 QGIS 算法面板，把 15 个包收敛到 7 个、客户端面收敛到 2 个，并把第一阶段拆成"无客户端 1a / 有客户端 1b"；同时给每个阶段补上可执行的退出条件与数字阈值、给全程补上人周估算——现在唯一的工作量数字是"2–3 天"。
