# 运行时契约（实测汇总）

> 本文汇总 M0 / M1a / M1b 三轮实测中发现的**契约陷阱**，是《方案设计》3.7 与附录 I 的配套收口。
>
> **一条共同的形态**：下面每一条的**类型都是对的、编译期都不报错、单元测试也都发现不了**。
> 它们只在「装进 profile、起真实实例、驱动真实界面或真实外部工具」时暴露，
> 而且**几乎全部是静默失败**——没有异常、没有日志，只是行为不对。

## 一、宿主与服务（node 半）

| # | 契约 | 类型怎么说 | 运行时实际怎样 |
|---|---|---|---|
| 1 | 插件注入声明 | 函数形式与类形式都能写 | **函数形式用 `export const inject`；类形式必须用 `static readonly inject`**。类形式下模块级导出被**静默忽略**，直到你访问注入的服务才抛 `cannot get property "x" without inject` |
| 2 | 服务类字段 | `#private` 与 `private` 都是私有 | **Cordis 用 `Proxy` 分发服务，`#private` 不穿过 Proxy**：`Cannot read private member #x from an object whose class did not declare it`，整行激活失败。必须用 TS 的 `private` |
| 3 | `ctx.subprocess.spawn` | `stdio` 看着像字符串 | `stdio` 是**对象** `{ stdin, stdout, stderr }`，且**该接缝不施加任何默认值**——`stdin` 也必须显式声明 |
| 4 | 等待子进程 | 直觉是 `wait()` | 句柄提供 **`done`**（`Promise<SubprocessOutcome>`）与 `waitForExit`，**没有 `wait`**。`'pipe'` 时原始流归调用方，必须与 `done` **并发排空** |
| 5 | `spawn` 的 `cwd` | 看着可选 | **必须显式传**。省略会抛 `TypeError: Cannot read properties of undefined (reading 'includes')`——来自一个在墓碑过滤**之前**运行的空字节校验，报错与真实原因无关 |
| 6 | 访问 `ctx.<service>` 的类型 | 服务在各自包里 | 必须 `import type {} from '<声明它的包>'`，否则 `Property 'x' does not exist on type 'Context'`。**已在 `slots`/`locale`/`systemPrompt`/`skills`/`sandbox`/`subprocess` 六处重复出现** |
| 7 | 依赖通道 | 按语义选 dist-tag | `@deepseek-ai/dsh-*` 的 **`latest` 是陈旧的 `0.0.1-rc.1`**，且经镜像安装会因依赖一个**从未发布**的包而失败。必须锁 **`alpha`** |
| 8 | 构建脚本门禁 | 以为只影响 git 安装 | **纯 npm 依赖同样会被 `ERR_PNPM_IGNORED_BUILDS` 拦下**（本次是 esbuild），profile 需要 `allowBuilds` |

## 二、客户端半（browser 半）

| # | 契约 | 类型怎么说 | 运行时实际怎样 |
|---|---|---|---|
| 9 | `clientBundle()` 的产物 | 以为只产出浏览器半 | **必须同时产出 node 半**。客户端包的 Loader 行按**裸包名**解析到 `lib/index.js`，缺了就直接 **`failed to import`** |
| 10 | eager / lazy 图 | 共享模块天经地义 | **eager 与 lazy 图之间不得共享任何模块**（最易犯的是共享 CSS Module）。rolldown 会把它提升为共享 chunk，入口出现**同步 `require("./client.x.js")`**，而加载器协议禁止 entry/chunk 同步 require |
| 11 | 插槽的 `form` | 文档与示例都暗示会传入 | `plugins.bundle.config` **永不传 `form`**（页面只传 `{ view: 'page' }`）；只有 `plugins.row.config` 由页面注入。**bundle 卡片必须自取** |
| 12 | 插槽的类型检查 | 照抄仓内 import | 必须 import **声明该插槽的包**；且 **`dsh-client-ui-slots` 只有 `.` 导出、没有 `/client` 子路径**，照抄仓内写法会报模块找不到 |
| 13 | `.volatile()` 的 Config | 教程示例带注解 | **不能加 `Schema<Config>` 标注**——`exactOptionalPropertyTypes` 下 `Volatile<string>` 与 `string` 冲突。教程示例是非 volatile 的，照抄就错 |
| 14 | 内容型工具输出 | `ContentBlock` 像在 tools 包 | `ContentBlock` 来自 **`@deepseek-ai/dsh-llm`**，不是 `dsh-tools`。且 `output.schema.type` 需要 **`as const`**，否则拓宽成 `string`，`execute` 返回类型退化为 `never` |

## 三、设置与 Plugins 页（**一个 row 牵涉三个不同的 id**）

| 用途 | 值 | 来源 |
|---|---|---|
| `plugins.row.config` 槽 key | `` `${bundle}#${rowId}` ``，如 `@znlgis/dsh-gis#gis-gdal` | `rowConfigKey()`，ledger 由**客户端槽注册**驱动 |
| `ctx.configForms.get()` 命名空间 | `entry.options.id`，如 `gis-gdal` | 宿主 `settings.describe()` |
| `li[data-plugin-row]` | Loader **entry id**，如 `include:gis-gdal` | DOM 属性 |

**混淆任意两个都静默失败**：没有异常、没有日志，只是入口不出现或表单不可写。

### 三条最贵的教训

1. **停用的行没有设置命名空间。** 症状是「表单存在但 `status` 为 `unavailable`」。我为这一个 checkbox 在客户端上改了三轮 id 拼写。判定顺序应当是：**先看行的启用状态 → 再看命名空间 → 最后才是 id 拼写**。
2. **`ctx.configForms.get()` 对不存在的命名空间不报错、不返回 undefined**，而是返回一个**看起来完全正常的表单对象**，`writable` 甚至为 `true`。**只有 `getSnapshot().status` 能分辨**。任何「取到表单就算成功」的判断都是错的。
3. **命名空间的发布有四条充分必要条件**（`settings/src/index.ts:302`）：条目被 `configEditor.configuration()` 收录、`entry.fiber.runtime.Config` 存在、schema 至少有一个 `.volatile()` 字段、`entry.fiber.state === ACTIVE`。**命名空间就是 `entry.options.id`，没有前缀换算规则。**

## 四、数据与格式

| # | 契约 | 运行时实际怎样 |
|---|---|---|
| 15 | `dataset.title` | 是**显示名**，对 shapefile 就是裸文件名。**永远不要进 argv**——GDAL 会拿它去工作目录里找，报 `No such file or directory`。按 kind 取 `dir`/`main`/`path` |
| 16 | 多几何体 WKT 序列化 | `MULTIPOINT` / `MULTILINESTRING` / `MULTIPOLYGON` 必须给**整个成员表**再包一层括号。缺了就是**无效 WKT**。三处同一系统性错误，只有 `parse → serialize → 断言等于原文` 的往返测试能发现 |
| 17 | GDAL 的价值 | `ogrinfo -j` 在 `coordinateSystem.projjson.id.code` 里**直接给出 EPSG 码**；手写 `.prj` 解析器只能靠名字猜。这是 GDAL Provider 存在的唯一理由 |

## 五、方法论

1. **「类型正确」与「运行时寻址/生命周期正确」是两件事。** 本文 17 条里有 14 条属于后者。
2. **真实实例验证不可省。** `Proxy` 吞私有字段、停用行无命名空间、`title` 当路径——**没有任何一条能被单元测试发现**。M0 之所以要设一道真实实例门，就是为此。
3. **但真实实例并非唯一手段。** M1b 的 GDAL 链路靠**结构化解耦**（把 `runtime.run` 抽成接口）在单元测试里驱动了真实二进制——**不需要模型凭据**。遇到「必须起实例/必须有凭据」的判断时，先问一句：真正的依赖能不能抽出来。
4. **断言要断言结构，不要断言「跑成功了」。** 出图测试断言「颜色多于 3 种」和「孔洞中心等于背景色」，而不是「文件生成了」；WKT 断言往返相等，而不是「解析成功」。本文一半的 bug 是这类断言抓出来的。
