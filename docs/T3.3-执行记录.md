## 三、三个设计决定（都是为了避免用户会看到的那种 bug）

1. **分页必须有序**：`LIMIT/OFFSET` 没有 `ORDER BY` 时**顺序未定义**，第 2 页可能重复或漏掉第 1 页的行。排序键用主键；**无主键时退回 `ctid`**（对单次查询稳定，且页面**如实报告**用了哪个键），复合主键也退回 `ctid` 而不是假装有序。
2. **几何由数据库编码**：`ST_AsGeoJSON` 在库里跑（geography 先 `::geometry`），于是页面携带的是坐标而不是 WKB 十六进制，工具层不必在 JS 里解析几何格式。
3. **超限分页拒绝**：要 5000 行只给 500 行是那种最终会进到导出文件里的谎言 ⇒ `LIMIT_EXCEEDED`，让调用方自己翻页。

## 四、判据的实测（真库 35/35）

- **慢查询 → `SQL_TIMEOUT`** ✓：剖面 `statementTimeoutMs: 500` 下跑 `SELECT pg_sleep(3)`，得到 `SQL_TIMEOUT`，且**耗时 < 2.5 s** ⇒ 是**服务器掐断**的，不是等完再判 ✓
- **写操作被拒** ✓：两个剖面都实测 `CREATE TABLE` 被**数据库**拒绝（`default_transaction_read_only=on`），不是被某条代码路径拦住 ✓
- 分页：5 条一页 ✓、`orderBy === 'id'` ✓、满页报 `hasMore` ✓、**第 2 页与第 1 页无重叠** ✓（这才证明确实有序）、无主键表的 `orderBy === 'ctid'` 且仍可分页 ✓、**geography 列也能翻页** ✓、属性全部 JSON 安全 ✓、空间列与载体列**都不混进 properties** ✓、超限被拒 ✓

## 五、诚实边界

1. **分页仍未被工具层使用**：`page()` 已在服务上可调用，但 `gis_inspect`/`gis_query` 还没接进去（T3.6 多图层贯通时一起）。
2. **偏移分页的固有代价**：大表深翻页时 `OFFSET` 会让数据库扫描跳过的行；键集分页（`WHERE id > :last`）更快但要求调用方记住上一页的键——本轮选了简单且可预测的那条，未做键集分页。
3. **`ctid` 不是键**：并发的 `UPDATE` 会移动行 ⇒ 无主键表的翻页在并发写入下可能重复/跳过。这是如实告知的取舍，不是缺陷掩盖。
4. **没有连接池上限的压测**：池 `max: 4` 是拍的，未测并发。
6. **一条已知抖动测试**：`packages/ui-gis/tests/blob-route.spec.ts` 的 multipart/byteranges 用例在整轮并发跑时偶发失败（单独重跑与再次全量均 19/19 通过 ✓）。它属于 T2.3 的产物，怀疑与计时/并发有关，未定位——如实记下而不是当它不存在。
5. **LIMIT/OFFSET 是校验后的整数内插**，不是绑定参数（`$1`）——两者都安全，但注释与实现一度不一致，已改正并写进模块文档。
