## 三、🔴 M3 期间抓到的真问题（都是「真环境才能暴露」这一类）

| 现象 | 真因 | 处置 |
|---|---|---|
| Loader 行**静默不加载**（服务永不出现、零告警） | 入口形状：只导出 `apply` 的模块不被装配 | 改**默认导出 Service**（契约 #42 结案） |
| 整个 harness 起不来，报错指向用户从没配过的插件 | 凭证引用含连字符 + 凭证文件旧扁平格式 | 引用必须 `[A-Za-z_]\w*`、文档必须 `version: 1` + `refs:`；我们的 schema 前移拦截（#44/#45） |
| 目录查询被服务器直接拒绝 | `geometry_columns` 用 `f_` 前缀旧列名 | 照真实列名写（#46） |
| 几何类型比较永远不匹配 | 目录返回大写 `POINT` | 边界归一化 + **显式映射表**（#47） |
| 指定 layer 的 inspect 返回全部图层；缺 layer 的 query 报空消息错误 | 多图层容器从未被测过 | inspect 只描述被点名那层；缺 layer 由我们给 `LAYER_AMBIGUOUS`（#22r） |
| **真实例检查全红**，与业务代码无关 | 内核 rc.1 → rc.2，pin 未跟 ⇒ **bundle 被静默跳过**（契约 #34 首次真实发生） | 22 处 pin 升 rc.2；**无需改一行源码**即恢复（#22s） |

## 四、诚实边界（M3 结束时仍未做）

1. **PostGIS 尚未接入工具层** ✗：目录/分页/瓦片/过滤器都在**服务层**可用并被真库验证 ✓，但 `gis_inspect`/`gis_query` 还只走 handler（GDAL/纯 JS）路径 ⇒ 模型今天**看不到** PostGIS 数据。**这是 M3 之后的第一补项**（也是 T3.6 记录里已写的边界）。
2. **`gis-postgis` 的 bundle 行仍未挂** ✗：给新包加行需要「重装 profile」这一步（否则所有已装 profile 每次启动报 `failed to import`）。行与重装步骤一起做。
3. **没有真正的低版本 GDAL 环境** ✗：计划 F6 提到备一份低版本 GDAL 用于断言升级诊断；本轮用**可注入的版本**覆盖了门槛与键 ✓，但「真机上装旧 GDAL」的路径未验。
4. **没有真 PostGIS 容器** ✗：用的是**本机** PostgreSQL 17.5 + PostGIS 3.5.2 ✓（判据全部在该库上通过）；计划 F7 指的是容器化的可复现环境，未做（Docker 守护进程未运行）。
5. **未做模糊/随机安全测试** ✗（只有手工构造的注入与错误）；GDAL 路径的注入面未做针对性测试（参数经 `argv` 无 shell ✓）。
6. **`.gdb` 数据集注册表里的 `layers` 仍是占位** ✗（opener 同步、枚举需跑 GDAL）；真相在 `inspect` 的结果里 ✓。
