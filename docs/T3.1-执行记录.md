## 三、判据是「机械成立」的

schema 用 `z.strictObject` 且**没有** password 字段 ⇒ 配置里写 `password: …` **直接加载失败并点名该键** ✓。这比「写文档提醒不要放密码」强，也比「只允许从环境变量读」强——后者仍然允许被写下来。

## 四、单测（10/10）

明文密码被拒（裸的、以及从别的工具迁移最可能写的那种）✓；**凭证引用必须匹配凭证文档自己的正则**（`postgis-city` 被拒、`postgis_city` 通过）✓；默认值（5432 / ssl=false / 15s）✓；**`describe()` 只调用 credentials 的 `describe`、从不调用 `resolve`**（记录型解析器断言调用序列 ✓）；用**真 `LocalCredentialProvider`** 往返：存入 → configured → `resolve()` 拿得到 → `redact()` 把连接串里的密钥抹成 `***` ✓；无凭证服务 → `unavailable` ✓。

两次启动。**好的一侧**：行装配并发布 `ctx.gisPostgis` ✓、两个剖面都被描述 ✓、隔离凭证文件里的引用读作 **configured** ✓、无凭证的剖面 `not-required` ✓、默认值到达运行中的服务 ✓、**所有必需插件都激活** ✓、**密钥不出现在实例日志里** ✓。**坏的一侧**（独立工作目录、只有那一行）：明文密码**不使服务发布** ✓、但**不拖垮整个 harness** ✓、探针照常运行 ✓、**被拒的值本身不被回显** ✓。

## 六、🔴 三个只有真实例才能暴露的坑（全部已进契约）

1. **入口形状**（契约 #42 结案）：只导出 `apply` 的模块**既不报错也不加载**——服务永远不出现、日志零告警。必须 `name`+`apply` 或**默认导出 Service**（本仓 gis-core/gis-gdal 是后者）。隔离 cordis 里能注册完全不能说明 Loader 里能装配。
2. **凭证引用不能有连字符**（契约 #44）：`postgis-city` 让**凭证插件**解析文档失败 ⇒ **整个启动失败**，报错指向一个用户从没配置过的插件。已加同一条正则到我们自己的 schema，在配置层就拦住。
3. **凭证文件是 `version: 1` + `refs:` 嵌套**（契约 #45）：旧的扁平 `key: value` 是预发布格式，同样导致启动失败，而症状是「探针一直不报告」（离原因很远）。

另有两条与代码无关的方法论教训：**构建没输出 ≠ 构建成功**（缺 `tsdown.config.ts` ⇒ 产物在 `dist/` 而 `main` 指 `lib/`，白查三轮）；**等待探针要等「结论」而不是「打招呼」**（等待模式匹配到 `probe-loaded` 会立刻返回，然后读到空 ✗）。
