## 三、两条绝对规则

1. **任何值都不进 SQL 文本**：字面量一律成为 `$n` 参数 ✓ ⇒ 含引号、分号、甚至 DROP 的值**只是一个值** ✓。
2. **任何标识符必须出现在调用方的白名单里**：列名无法绑定（SQL 没有标识符占位符 ✗），所以唯一安全的做法是要求它确实是**该图层的列** ✓；未知列**点名拒绝**（并列出可用列 ✓），绝不静默忽略——静默忽略会返回调用方没要的行 ✓。

白名单来自**数据库自身**（`pg_attribute` ✓），不是来自请求 ✓ ⇒ 调用方无法通过点名一个不存在的列来放宽它 ✓。

## 五、🔴 一个与纯 JS 路径**不一致**的取舍（如实记录）

`name = 'x'' OR ''1''=''1'` 这种「把恒真式塞进引号里」的尝试，在**两条路径上都是被拒绝**的 ✓——因为分词器（找 AND/OR 的那个）**不识别引号** ✓，而这与纯 JS 路径**刻意保持一致** ✓（同一句 where 在 GeoJSON 与 PostGIS 上应当同义 ✓）。

拒绝是安全的 ✓；把它当作「一个奇怪的值」绑定也安全 ✓。选了前者，理由是**更诚实**（调用方写的确实是歧义文本 ✓）。这条取舍写进了测试注释，避免后人误以为是漏洞。
