# Fact-check report: docs/方案设计.md domain-technical claims

Verified 2026 (live HTTP probes, official specs, driver/library sources).

## 1. WMS axis order — VERDICT: CORRECT
WMS 1.1.1 indeed uses SRS + BBOX=minx,miny,maxx,maxy (x,y); WMS 1.3.0 renamed the param to CRS and, for geographic CRSs whose authority axis order is northing,easting (EPSG:4326, 4258...), the BBOX must be lat,lon (miny,minx,maxy,maxx); projected CRSs such as EPSG:3857 are unaffected. CRS:84 is a real OGC CRS ("WGS 84 longitude-latitude") and is the canonical workaround — MapServer's own docs show CRS=CRS:84&BBOX=-180,-90,180,90 vs CRS=EPSG:4326&BBOX=-90,-180,90,180. Caveat to add: CRS:84 must be advertised in GetCapabilities and some servers do not offer it (and a few deliberately ignore axis order, e.g. GeoServer's "Force XY"); keep a per-service axis-order override instead of trusting CRS:84 blindly.
Sources: https://mapserver.org/ogc/wms_server.html ; https://www.opengis.net/def/crs/OGC/1.3/CRS84 ; OGC WMS 1.3.0 (06-042) https://portal.ogc.org/files/?artifact_id=14416

## 2. WFS paging — VERDICT: CORRECT (incomplete)
count + startIndex and numberMatched/numberReturned are correct for WFS 2.0 (OGC 09-025r2 §7.6.3/§7.7); maxFeatures is correct for 1.1.0 — the 1.1.0 schema has maxFeatures and NO startIndex (wfs.xsd 1.1.0, GetFeatureType). Missing details worth adding: (a) WFS 2.0 stored queries are 4 of its 11 operations (CreateStoredQuery / DropStoredQuery / ListStoredQueries / DescribeStoredQueries); (b) responses may carry next/previous link attributes, and numberMatched may be the literal "unknown" (xsd:nonNegativeIntegerOrUnknown); (c) startIndex is 0-based since the 2.0.2 clarification but MapServer <= 6.2 counted from 1 (GDAL exposes OGR_WFS_BASE_START_INDEX); (d) STARTINDEX with WFS 1.0/1.1 is a vendor extension (MapServer >= 6.0), not spec; (e) servers may ignore/cap paging, so clients must auto-detect (GDAL: "will automatically detect if server supports paging"; default page size 100) and detect no-progress loops rather than assuming startIndex works.
Sources: https://docs.ogc.org/is/09-025r2/09-025r2.html ; https://schemas.opengis.net/wfs/1.1.0/wfs.xsd ; https://gdal.org/en/stable/drivers/vector/wfs.html

## 3. WMTS — VERDICT: CORRECT (imprecise flip condition)
ScaleDenominator + TopLeftCorner, per-matrix TileWidth/TileHeight (256 typical, 512 common; TMS 2.0: "typically 256x256 or 512x512"), and dual KVP/RESTful encodings via ResourceURL (SOAP exists too) are all correct. Precision needed: WMTS 1.0.0 defines the origin as the TopLeftCorner = (min x, max y) of the matrix and TileRow/TileCol 0,0 "next to the top left corner ... increas[ing] towards the right and towards the bottom" — OGC TMS 2.0 Table 8 notes topLeft was "the only possibility available in WMTS 1.0", while bottomLeft ("tms" convention) only became first-class in TMS 2.0. So a Y-flip is NOT needed for conformant WMTS 1.0 sets (e.g. GoogleMapsCompatible/WebMercatorQuad: origin -20037508.34,20037508.34, TileMatrix=z, TileCol=x, TileRow=y), and is needed only when the matrix's corner of origin is the bottom-left. Robust recipe: pixelSpan = scaleDenominator*0.28e-3/metersPerUnit; tileSpanX = tileWidth*pixelSpan; TileCol = floor((tileMinX-originX)/tileSpanX); TileRow = floor((originY-tileMaxY)/tileSpanY) for a top-left origin, TileRow = floor((tileMinY-originY)/tileSpanY) (= MatrixHeight-1-y for square power-of-two matrices) for bottom-left. Also: TopLeftCorner coordinates follow the CRS axis order (OpenLayers swaps them when the projection axis orientation starts with "ne"), substitute the REST template variables by name ({TileMatrix}/{TileRow}/{TileCol}), and honour TileMatrixSetLimits.
Sources: https://docs.ogc.org/is/07-057r7/07-057r7.pdf (clause 6.1, Annex H); https://docs.ogc.org/is/17-083r4/17-083r4.html (Table 8, cornerOfOrigin); https://github.com/openlayers/openlayers/blob/main/src/ol/source/WMTS.js

## 4. GDAL OpenFileGDB — VERDICT: WRONG / OUTDATED
Read support is built in since GDAL 1.11.0 (2014: "New OGR drivers: ... OpenFileGDB: read-only support (no external dependency)"), NOT 3.4. Write and update support has been in OpenFileGDB since GDAL 3.6.0 with no external dependency ("same (and actually larger) functional scope as write side of the FileGDB driver"), and since GDAL 3.11 the SDK-based FileGDB driver delegates creation/update to OpenFileGDB; raster read came in 3.7. The "non-redistributable proprietary SDK" premise is also outdated: Esri publishes the File Geodatabase API at github.com/Esri/file-geodatabase-api under Apache-2.0 (License.txt + README "Copyright 2017 Esri, Licensed under the Apache License, Version 2.0"). Remaining true limits: ArcGIS 9.x .gdb is read-only, SDC/CDF-compressed data still needs the SDK, and OpenFileGDB writes the v10.x format only — so "GDB is read-only in practice, write requires a non-redistributable SDK" is wrong today; writing .gdb works with stock GDAL >= 3.6.
Sources: https://gdal.org/en/stable/drivers/vector/openfilegdb.html ; https://raw.githubusercontent.com/OSGeo/gdal/v1.11.0/gdal/NEWS ; https://github.com/OSGeo/gdal/blob/master/NEWS.md (3.6.0, 3.11.0) ; https://gdal.org/en/stable/drivers/vector/filegdb.html ; https://github.com/Esri/file-geodatabase-api

## 5. PostGIS — VERDICT: CORRECT (caveats confirmed)
ST_EstimatedExtent exists, reads the geometry column's statistics and is "usually much faster" than ST_Extent — but with no statistics (empty table or no ANALYZE/VACUUM ANALYZE) it returns NULL, and the value is only ~95% of the true extent (so cache it, never present it as an exact bbox). ST_AsMVTGeom + ST_AsMVT is the right server-side MVT pair, available since PostGIS 2.4.0 (feature-id support 3.0, parallel 2.5); generate bounds with ST_TileEnvelope (PostGIS 3.0+, margin 3.1+) and pre-filter rows with the index-friendly "geom && ST_TileEnvelope(...)" as in the PostGIS example; ST_AsMVTGeom requires geometry already in the tile CRS (ST_Transform) and JSON properties are not supported.
Sources: https://postgis.net/docs/ST_EstimatedExtent.html ; https://postgis.net/docs/ST_AsMVT.html ; https://postgis.net/docs/ST_AsMVTGeom.html ; https://postgis.net/docs/ST_TileEnvelope.html

## 6. COG/PMTiles + the DSH 200-only route — VERDICT: CORRECT
Both readers need byte-range service, and by default they FAIL (not merely slow down) on a 200-only server: pmtiles throws "Server returned no content-length header or content-length exceeding request. Check that your storage backend supports HTTP Byte Serving."; geotiff.js@3.0.5 (the pinned version) sets "Range: bytes=..." and throws "Server responded with full file" unless allowFullFile:true. So the doc's plan to build a 206/PARTIAL route is required, and its claim about the host route is right: the DSH test is literally named "ignores Range headers and returns complete bodies without advertising ranges" (media-references.host.spec.ts, /api/file, GET+HEAD, 413 over cap). Two precisions: Range is optional in HTTP ("A server MAY ignore the Range header field", RFC 9110 §14.2), so 200-with-full-body is legal HTTP and the breakage is client-side; and Accept-Ranges:bytes is informational — the decisive bits are 206 + Content-Range.
Sources: https://github.com/protomaps/PMTiles/blob/main/js/src/index.ts ; https://github.com/geotiffjs/geotiff.js/blob/master/src/source/remote.js ; https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2 ; D:\self\code\deepseek-harness\packages\api\session-controller\tests\media-references.host.spec.ts:124

## 7. Shapefile — VERDICT: PARTLY WRONG (2 GB claim)
Correct: GDAL reads the code page from .cpg, falling back to the DBF LDID, and SHAPE_ENCODING (config) / ENCODING (open option and layer creation option, i.e. -lco ENCODING=) is the right control; field names are limited to 10 characters ("Attribute names can only be up to 10 characters long"); Esri's KB confirms LDID/.CPG code-page detection. GBK/GB18030 (CP936/GBK, GB18030) are indeed the common legacy Chinese DBF encodings and .cpg values are often "GBK"/"936" (ArcGIS now defaults to UTF-8). Wrong/loose: 2 GB is not a format limit — the .shp uses 32-bit offsets in 16-bit words, GDAL states the format "cannot go over 8GB" and the OGR implementation caps at 4 GB, adding "it is not recommended to use a file size over 2GB for both .SHP and .DBF files" (2GB_LIMIT=YES / SHAPE_2GB_LIMIT enforce it). The familiar 2 GB figure is the practical Esri/ArcGIS per-file limit (Esri Japan KB: a 2 GB per-file limit, "not a 2 GB limit for the shapefile as a whole"). Say "2 GB practical/.shp+.dbf per-file limit, 4 GB GDAL implementation cap".
Sources: https://gdal.org/en/stable/drivers/vector/shapefile.html ; https://support.esri.com/en-us/knowledge-base/read-and-write-shapefile-and-dbase-files-encoded-in-var-000013192 ; https://tech-support.esrij.com/arcgis/article/web/knowledge2494.html

## 8. RFC 7946 GeoJSON — VERDICT: CORRECT
§4: all coordinates are WGS 84, "longitude and latitude units of decimal degrees", equivalent to urn:ogc:def:crs:OGC::CRS84, and the alternative-CRS mechanism was removed (the 2008 spec's "Coordinate Reference System Objects"/crs member is obsolete). §3.1.1: "The first two elements are longitude and latitude, or easting and northing, precisely in that order". Real-world violations are real and worth detecting: the 2008 spec legitimised a crs member (so legacy files can declare a projected CRS), and lat/lon order confusion is the classic EPSG:4326-vs-leaflet mistake. Note the doc's "coordinates outside [-180,180]/[-90,90] => projected" test is only a heuristic (it misses projected metres that happen to fall in range and would also reject legal-looking but non-conformant data), so report it as a warning with the raw bbox rather than a hard error.
Sources: https://www.rfc-editor.org/rfc/rfc7946.html#section-4 ; https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.1 ; https://geojson.org/geojson-spec.html (obsolete 2008 spec, §3)

## 9. CORS — VERDICT: PARTLY WRONG
The mechanism is right: MapLibre GL JS sets image.crossOrigin='anonymous' for cross-origin raster URLs (v6.11.0 image_request.ts:261-262), so WebGL texture upload from a non-CORS server fails, and fetch-based readers need CORS anyway. But "the vast majority of WMS/WMTS servers send no ACAO" is not supported: I probed live and 6 of 8 major public services DID return Access-Control-Allow-Origin: * — OSM tiles, NASA GIBS WMTS + WMS, USGS National Map WMTS, Esri ArcGIS Online imagery, swisstopo WMTS, PDOK WMTS, MapServer demo WMS, Spain IGN WMS — while NRW DOP WMS (www.wms.nrw.de) and Esri sampleserver6 WMS sent none. So CORS is inconsistent, not absent: keep the proxy for credentials/caching/uniform errors (reasons 2 and 3 are solid), but drop the absolute wording. Also note plain <img>-based layers (Leaflet) need no CORS at all — this is a WebGL/fetch constraint.
Sources: https://github.com/maplibre/maplibre-gl-js/blob/main/src/util/image_request.ts#L260-L262 ; live header probes of the URLs above

## 10. Licenses — VERDICT: WRONG on FlatGeobuf, all others correct
FlatGeobuf is wrong: the LICENSE shipped in the flatgeobuf@4.4.0 npm tarball (and the repo root LICENSE) is BSD-2-Clause, and the implementation sub-licenses (src/cpp/LICENSE, src/ts/LICENSE) are ISC; only npm's metadata field says BSD-3-Clause, which is what the doc evidently copied. Everything else checks out: GDAL MIT (gdal.org license: "In general, the GDAL/OGR source code is licensed under the MIT license"), QGIS and PostGIS GPL-2.0-or-later (COPYING is GPLv2 and source headers say "version 2 ... or (at your option) any later version" — write GPL-2.0-or-later, not bare GPL-2.0), MapLibre GL JS BSD-3-Clause (LICENSE.txt has the three clauses), deck.gl MIT, geotiff.js MIT, shpjs MIT, @turf/turf MIT, PMTiles BSD-3-Clause, DuckDB MIT, CesiumJS Apache-2.0, OpenLayers BSD-2-Clause, proj4 MIT, fast-xml-parser MIT, saxes ISC — all matching the npm registry license fields, as do @terraformer/wkt MIT, @loaders.gl MIT, geojson-vt ISC, @mapbox/vector-tile BSD-3-Clause, @math.gl/web-mercator MIT, pg MIT, postgres Unlicense, @duckdb/node-api MIT, gdal-async Apache-2.0.

## Other wrong/misleading domain claims in the document
1. GML parsing profile is WFS 1.1-shaped (line ~744): "wfs:FeatureCollection -> gml:featureMember" does not match WFS 2.0, whose GML 3.2 responses wrap features in wfs:member (the string gml:featureMember does not occur in OGC 09-025r2; GDAL's WFS driver notes it "wrap[s] the features inside a WFS 2.0 wfs:FeatureCollection / wfs:member element"). A parser that only looks for gml:featureMember silently returns zero features on standard WFS 2.0 servers — the doc's own "never silently drop geometry" rule is violated. Add gml:featureMembers too (WFS 1.0/GML2).
   https://docs.ogc.org/is/09-025r2/09-025r2.html ; https://gdal.org/en/stable/drivers/vector/wfs.html
2. qgis_process version (line ~817): introduced in QGIS 3.14 ("New standalone console tool for running processing algorithms", QGIS 3.14 changelog; first commit 2020-04-09 renaming qgis_transform to qgis_process), not "QGIS 3.24+".
   https://changelog.qgis.org/en/qgis/version/3.14/
3. "TileMatrixLimits out of range -> return a transparent tile" (line ~761) is only safe for transparent layers: WMTS 1.0.0 says such a request "SHOULD result in an exception response", and for an opaque basemap a transparent hole looks like missing data. Prefer answering 404/204 locally and letting the client decide.
   https://docs.ogc.org/is/07-057r7/07-057r7.pdf
4. "WMTS is naturally a map source — MapLibre raster tiles directly usable" (line ~696): MapLibre has no WMTS source and its raster template only substitutes {z}/{x}/{y}; it works only for XYZ-compatible matrix sets. Non-trivial matrix sets (ScaleDenominator mapping, row/col ordering, bottom-left origin) require the adapter the doc later designs — so the proxy route should be described as mandatory, not an optimisation.
   https://maplibre.org/maplibre-gl-js/docs/API/classes/RasterTileSource/
5. Minor: the document mixes WFS 2.0's GeoJSON mime type; the OGC GeoJSON output format is usually advertised as application/json (or application/json; subtype=geojson), and WFS 2.0's default is GML 3.2 — worth stating explicitly in the format negotiation list.
