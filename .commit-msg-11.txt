feat: T3.5 — geodatabase reading, version gates, and diagnostics that are keys

gdb.ts answers two questions: can this GDAL read a file geodatabase, and what do
we TELL the user when it cannot.

- parseGdalVersion handles the real string, two-part versions, and development
  builds (marked as such rather than mistaken for a release)
- the gates are 1.11 for reading and 3.6 for writing, asserted ON the boundary
  (1.10.9 refused, 1.11 accepted; 3.5.3 refused, 3.6 accepted)
- a diagnostic is { key, detail }, never a finished sentence: a sentence built
  here cannot be translated, and a test that matches one fails every time the
  wording improves. The acceptance criterion asks for the key, and the key is
  what the tests assert.
- the WRITE gate exists to EXPLAIN, not to gate: this build is read-only by
  product decision, so a user with a new-enough GDAL is told the capability
  exists (gdb.write.available, readOnly: true) and a user with an older one is
  told what was found and what is needed
- OpenFileGDB is PROBED (ogrinfo --formats), not assumed
- a version below the read gate refuses WITHOUT invoking the binary at all

Verified with 12 unit tests and 13 assertions against the real GDAL 3.13.3
(check:gdb): the driver is present, the version parses, reading is allowed, the
committed cities.gdb enumerates its feature class with a geometry type, and an
old GDAL is refused by key with zero external calls.

"Does not write" is asserted structurally: no exported FUNCTION matches
write/create/update/delete/insert -- writeDiagnostic only describes the
capability. A promise the module cannot break is worth more than one in a doc.

238 node tests + 1 skipped, 13 web tests, bundle contract OK.
