feat: T3.6 — the layer parameter reaches everything that reads a dataset

A multi-layer fixture first (tests/fixtures/multi.gdb, 63 KB, two feature
classes: cities in 4326 and projected_areas in a projected CRS), because a
single-layer fixture cannot show that layers are handled at all.

The plumbing turned out to be nearly there: QueryRequest already carried layer,
and the GDAL handler already passed it as -layer. What was missing was the tool
schemas -- gis_query and gis_render had no layer parameter -- so the parameter
now travels from the model to the handler.

The fixture immediately exposed two REAL defects, both of which only a
multi-layer dataset can show:
- inspect(dataset, 'cities') returned EVERY layer, with the extent and fields
  taken from whichever came first: it described a container while looking like it
  described the layer you named. It now filters to the named layer.
- query without a layer on a multi-layer container produced ogr2ogr's error with
  an EMPTY message. Reading whichever layer happens to be first is the kind of
  answer that looks right and is not, so we now refuse it ourselves with
  LAYER_AMBIGUOUS, saying how many layers there are and what to pass.

Verified with real GDAL (check:gdb, 20 assertions): both feature classes are
listed, each can be described on its own, each can be READ with features and
geometry coming back, an unknown name gives LAYER_NOT_FOUND, and a layer-less
query on the container gives LAYER_AMBIGUOUS. On the tool side, four new tests
assert layer is offered in all three schemas, reaches gis_query, and -- the one
that matters -- reaches BOTH calls gis_render makes, because framing the picture
on one layer's extent and filling it with another's features is a wrong map that
looks like a right one.

Also recorded honestly: the registry's own dataset.layers for a .gdb is still a
placeholder named after the directory (the opener is synchronous and enumeration
needs GDAL), and the PostGIS side is not wired into the tools yet.
